toolchain: a standalone or host build on Porffor alpha 23 for macOS arm64 starts again (regression of 0.26.0, which made alpha 23 the default). The server bridge (`native-fetch-a22.c`) declared the generated main, `p__main__23main`, as a plain C function. Alpha 23 defines every generated JS function with `PORF_CC` (`swiftcall` on clang arm64, nothing elsewhere), so the call and the definition disagreed. That is harmless across separate object files for a function with no arguments, which is why no non-LTO build noticed, but the CLI's host and release builds link with `-flto`: LLVM sees the mismatch, turns the call into `unreachable`, and the binary died with SIGTRAP at `main+496` before it listened (`brk #1`, no output). The declaration now carries `PORF_CC` (defined as nothing when porf.h has none, as on alpha 22). Linux arm64 has the same convention (zig cc is clang) and was only spared because its default build is not LTO: a `--release` standalone for `linux-arm64` hit the same call. Linux x64 has no swiftcall and is unaffected; sproutd's generation (x86-64) is unaffected. Two new native tests keep it from returning: `test:native-lto` builds a server with `-flto -O3` and answers requests (startup, request, timer, promise), and `test:native-cc` compiles every unit and the bridge to LLVM IR for darwin and linux, arm64 and x64, and checks that every call, declaration and definition carries swiftcc exactly when its source declaration has `PORF_CC`. No app source changes and nothing an app can observe does (no compatibility date); a macOS or `--release` Linux arm64 build with toolchain 0.26.0 needs this release.
